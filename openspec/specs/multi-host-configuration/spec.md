# multi-host-configuration Specification

## Purpose
モジュールを複数の環境 (ホスト、利用側のリポジトリ) で使うための、環境固有の値と、プラットフォームによる分岐の扱い。構造を変える変更の証明のしかたも含む。

## Requirements
### Requirement: ホスト固有の値をモジュールから分離する

システムは、ホストや環境によって異なる値をモジュール内に直書きしてはならない (MUST NOT)。対象には、ユーザー名、ホスト名、git の identity と署名鍵、ssh の接続先、特定の環境でだけ使うパッケージ、プラットフォーム固有の外部プログラムのパスを含む。

値は利用側が与える。**モジュールがその値を読む場合に限り**、型付きの `dotfiles.*` の options として宣言しなければならない (SHALL)。モジュールが読まない値 (git の identity、ssh の接続先など) は option にせず、利用側が home-manager / nix-darwin の標準の option に直接書く (モジュールシステムがマージする)。

option を作る根拠は次のいずれかでなければならない (SHALL):

1. ホスト側が値を与える必要がある
2. 既定値を**ホスト依存の情報から導出する**必要がある (ホームディレクトリ、プラットフォーム等)

**定数を option に置き換えてはならない** (MUST NOT) — 指し先が増えるだけで何も表現しないため。「モジュールを整理したい」ことは option を作る根拠にならない (MUST NOT)。

ただし、**モジュール間でデータを受け渡すためのものはこの制限の対象外**とする。それは設定項目ではないため、`internal` を付けて設定項目と区別しなければならない (SHALL)。

#### Scenario: モジュールが読まない値

- **WHEN** 利用側が git の identity や ssh の接続先を与える
- **THEN** 利用側は `programs.git.settings.user.*` や `programs.ssh.settings.<host>` に直接書く
- **AND** そのための `dotfiles.*` の option は無い

#### Scenario: モジュールが読む値

- **WHEN** モジュールが環境ごとに違う値を読む (例: 署名鍵から `user.signingkey` を組み立てる)
- **THEN** その値は `dotfiles.*` の option で渡される
- **AND** 値が与えられないときの振る舞い (署名しないなど) が決まっている

#### Scenario: 既定値の導出による option

- **WHEN** option の値が現在すべてのホストで同一である
- **THEN** その既定値がホスト依存の情報から導出されていることが説明されている
- **AND** そうでない場合はその option は不要である

#### Scenario: モジュール間の受け渡し

- **WHEN** あるモジュールが導出した値を別のモジュールが必要とする
- **THEN** その受け渡しに使う option は `internal` として宣言される
- **AND** ホストが設定する対象ではないことが区別できる

#### Scenario: 誤った値の早期検出

- **WHEN** options に型の合わない値や存在しないオプション名を与える
- **THEN** 構成の評価が失敗する
- **AND** 実機への適用を待たずに CI で検出される

### Requirement: プラットフォーム固有の記述はモジュール内部で分岐させる

システムは、プラットフォームによって異なる記述を、ホスト側で分岐させてはならない (MUST NOT)。分岐は**モジュール内部で構成の評価時に**行わなければならない (SHALL)。

シェルスクリプトの実行時分岐 (`$OSTYPE` の判定等) で代替してはならない (MUST NOT)。評価時に決定できる事柄を生成物の実行時に判定すると、そのホストに不要な記述が生成物へ残る。

#### Scenario: プラットフォーム固有記述の閉じ込め

- **WHEN** 共有モジュールがプラットフォーム固有の記述を含む
- **THEN** その記述はモジュール内部で評価時に条件分岐されている
- **AND** 当該プラットフォームでないホストの生成物にはその記述が含まれない

#### Scenario: 実行時分岐の排除

- **WHEN** 生成されたシェル設定を確認する
- **THEN** プラットフォームを実行時に判定する分岐が含まれていない

#### Scenario: 依存の向き

- **WHEN** モジュールを実装する
- **THEN** モジュールはホストの宣言と利用側のリポジトリを参照しない (一方向依存)

### Requirement: 構造変更は振る舞い不変であることを証明する

システムは、ホストの構成を変えない目的の構造変更 (ファイル分割、モジュール化、値の options 化) を行う場合、**変更前後で生成される system の derivation path が一致すること**を確認しなければならない (SHALL)。一致しない場合、原因を特定して一致させるか、差分の理由を記録しなければならない (SHALL)。

#### Scenario: 分割前後の同一性の確認

- **WHEN** 振る舞いを変えない意図で構成ファイルを分割する
- **THEN** 分割前後の `toplevel` の derivation path が同一である
- **AND** 一致を確認するまで次の段階に進まない

#### Scenario: 差分が生じた場合

- **WHEN** derivation path が一致しない
- **THEN** derivation の差分を比較して原因を特定する
- **AND** 意図した変更であればその理由を記録する

#### Scenario: 撤回した変更の検証

- **WHEN** 一度入れた変更をスコープの見直しにより撤去する
- **THEN** 撤去後の derivation path が着手前のベースラインと一致する
- **AND** 撤去が完全であることがこれにより確認される
