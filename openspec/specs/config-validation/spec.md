# config-validation Specification

## Purpose
構成の破壊を、所有者の実機への適用ではなく PR の時点で検出する仕組みと、flake の入力を自動的な提案として更新する仕組み。

## Requirements
### Requirement: 構成の破壊は適用前に検出する

システムは、リポジトリへの変更提案 (Pull Request) の時点で flake 構成を評価し、破壊を検出しなければならない (SHALL)。所有者の実機への `switch` を、破壊に気づく最初の機会にしてはならない (MUST NOT)。

検証は**評価 (evaluation)** を必須とし、実ビルドは必須としない (MAY)。オプション名の変更・typo・モジュール衝突・入力の破壊的変更は評価の時点で顕在化するため。

検証の対象ホストは**宣言から取り出さなければならない** (SHALL)。ホストを追加したときに CI の定義を書き換える必要があってはならない (MUST NOT)。

#### Scenario: PR での構成評価

- **WHEN** `flake.nix` / `flake.lock` / `hosts/` / `modules/` 配下を変更する PR を作成する
- **THEN** CI が `nix flake check` と全ホスト構成の評価を実行する
- **AND** 評価に失敗した場合は PR のチェックが失敗する

#### Scenario: 評価対象の導出

- **WHEN** 新しいホストを宣言に追加した PR を作成する
- **THEN** そのホストが自動的に評価対象に含まれる

#### Scenario: 必須の出力が消えたことを検出する

- **WHEN** 常に存在しなければならない種類の出力 (macOS ホストを宣言する出力) が、リネームや削除によって存在しない
- **THEN** CI は失敗しなければならない (SHALL)
- **AND** 「宣言されていないためスキップ」として扱ってはならない (MUST NOT)
- **AND** その出力が空である場合も同様に失敗しなければならない (SHALL)
- **AND** 理由は「検証対象が無い状態は、検証が成功した状態と区別できなければならない」ことである

#### Scenario: 未宣言と評価失敗の区別

- **WHEN** ある種類の出力 (`homeConfigurations` 等) が宣言されていない
- **THEN** その出力はスキップされ、失敗として扱われない
- **AND** **「宣言されていない」と「宣言はあるが評価が失敗した」を区別しなければならない** (SHALL)
- **AND** 評価の失敗をスキップとして飲み込んではならない (MUST NOT)

#### Scenario: 評価環境の選択

- **WHEN** 対象ホストのプラットフォームが `aarch64-darwin` である
- **THEN** 評価が Linux runner 上で成立する場合はそれを用いる
- **AND** 成立しない場合 (IFD 等) は同一プラットフォームの runner へフォールバックする

### Requirement: 入力の更新は自動的な提案として受け取る

システムは、flake の入力 (`nixpkgs` / `nix-darwin` / `home-manager`) の更新を、**定期的に自動生成される Pull Request** として受け取らなければならない (SHALL)。更新を人手のきっかけに依存させてはならない (MUST NOT)。

#### Scenario: 定期的な入力更新

- **WHEN** スケジュールされた時刻になる
- **THEN** `flake.lock` を更新する PR が自動生成される
- **AND** その PR は構成評価の CI によって検証される

#### Scenario: 壊れる更新の遮断

- **WHEN** 入力の更新によって構成の評価が失敗する
- **THEN** 自動生成された PR のチェックが失敗し、マージ可能にならない
- **AND** 所有者の実機の構成は影響を受けない

#### Scenario: 更新 PR の滞留

- **WHEN** 前回の自動 PR が未マージのまま次回のスケジュールが実行される
- **THEN** PR が複数積み上がらない (同一ブランチが更新される)
