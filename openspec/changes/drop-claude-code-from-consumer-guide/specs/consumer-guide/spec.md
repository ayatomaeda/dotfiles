# Spec Delta

## MODIFIED Requirements

### Requirement: 利用側の作り方と運用の手引きを core に置く

システムは、利用側のリポジトリの作り方と運用の手引きを、core の `docs/CONSUMER-GUIDE.md` に置かなければならない (SHALL)。手引きの読み手は、core だけが見える端末で利用側のリポジトリを作って運用する人か、エージェントである。core の `README.md` と `CLAUDE.md` は、手引きへ案内しなければならない (SHALL)。

手引きは、少なくとも次を覆わなければならない (SHALL): 読み手と前提、利用側のリポジトリの形 (flake の inputs と follows、ディレクトリの分け方、エージェントに core の `CLAUDE.md` を読ませる場合の読み込み)、環境固有の値の置き方、core と利用側のどちらに置くかの判断、Homebrew の方針とその理由、日々の運用 (lock の更新、core だけを上げる更新の扱い、`--override-input` の範囲、switch を行う人、drvPath の照合、OpenSpec の進め方)、秘密の扱い、core を直したいときの手順、知見を返す経路。

手引きは、特定のエージェント製品 (Claude Code など) の宣言を、その製品を使う利用側の形として載せてはならない (MUST NOT)。その製品の宣言と注意は、それを使う利用側の文書が持つ。手引きが触れるのは、製品に依らない形 (利用側がエージェントの設定を持つこと、設定ファイルを宣言から生成するときの注意の種類) までとする。

#### Scenario: core だけが見える端末で読む

- **WHEN** core のクローンだけがある端末で、人かエージェントが利用側のリポジトリを作りはじめる
- **THEN** core の `README.md` か `CLAUDE.md` から `docs/CONSUMER-GUIDE.md` にたどり着ける
- **AND** 手引きだけで、利用側の `flake.nix` の inputs と、値を書くモジュールの置き場所が決められる

#### Scenario: 運用の手順を探す

- **WHEN** 利用側で作業する人かエージェントが、core の変更を利用側に入れる手順を探す
- **THEN** 手引きに、lock を更新したコミットから switch すること、`--override-input` は build と評価の確認だけに使うこと、switch は所有者が行うことが書かれている

#### Scenario: エージェントを使わない利用側で読む

- **WHEN** エージェントを使わない利用側が、手引きに従ってリポジトリを作る
- **THEN** 手引きの手順に、特定のエージェント製品の導入と宣言を前提にした段階が無い
- **AND** core の `CLAUDE.md` の読み込みは、エージェントに読ませる場合の形として書かれていて、読み込まない選択が手引きと矛盾しない

### Requirement: 利用側から知見を返す経路を手引きに書く

手引きは、利用側 (会社の構成など) から core と家へ知見を返す経路を書かなければならない (SHALL)。利用側から core と家へは直接送れないので、利用側で作業する人かエージェントは、返したい知見を利用側のリポジトリの中に申し送りとして書き残し、人間が持ち出す。申し送りは core に入りうるので、利用側の固有名を含まない形で書くことを、手引きは求めなければならない (SHALL)。

利用側から core を直接変える場合も core の公開の決まりに従うこと、所有者の家の端末にある公開の前の検査は利用側の端末に無いので、自分で確かめることを、手引きは書かなければならない (SHALL)。

#### Scenario: 会社の構成で見つけた注意

- **WHEN** 会社の構成で作業する人かエージェントが、core に足すべき一般的な注意を見つける
- **THEN** 手引きに従い、その注意を会社のリポジトリの中に、会社の固有名を含まない申し送りとして書いている
- **AND** core や家のリポジトリへ直接書き込もうとしていない

#### Scenario: 利用側の端末から core に PR を出す

- **WHEN** 利用側の端末で作業する人かエージェントが、core に変更を提案する
- **THEN** 手引きに、その端末には公開の前の検査が無いこと、コード・コミットメッセージ・ブランチ名・PR の文章に固有名が無いことを自分で確かめることが書かれている

## REMOVED Requirements

### Requirement: 手引きに私的な情報を書かない

**Reason**: Scenario「Claude Code の宣言を載せる」が特定のエージェント製品を名指ししている。Scenario の差し替えは MODIFIED ではできないので、要件を置き換える。

**Migration**: 同じ本文と Scenario「公開の前の検査」を、下の「手引きに私的な情報と資格情報の値を書かない」が引き継ぐ。「Claude Code の宣言を載せる」は製品名の無い「利用側のツールの宣言を載せる」になる。

## ADDED Requirements

### Requirement: 手引きに私的な情報と資格情報の値を書かない

手引きは core の文書なので、core の公開の決まりに従わなければならない (SHALL)。家の固有名 (ホスト名、ドメイン、アドレス、ネットワークとクラスタの構成、認証基盤の値、ユーザー名、家でだけ使うアプリとツールの名前) を書いてはならない (MUST NOT)。家に固有の部分は、その種類 (クラスタへの接続の宣言、家でだけ使う cask など) を書くまでに留める。

コード片は、固有名を役割の名前やプレースホルダに置き換えて載せてよい (MAY)。秘密の値と、秘密として扱わない資格情報の値 (API キーなど) は、置き換えずに載せてはならず、その値を読むファイルの中身を手引きに写してはならない (MUST NOT)。家のリポジトリのコミットのハッシュを書いてはならない (MUST NOT)。

#### Scenario: 利用側のツールの宣言を載せる

- **WHEN** 手引きに、家のツールの宣言 (資格情報を読むものを含む) をコード片として載せる
- **THEN** 資格情報は値ではなく、利用側のファイルから読む形だけが書かれている
- **AND** 家のユーザー名、ホスト名、家でだけ使う設定の名前が含まれていない

#### Scenario: 公開の前の検査

- **WHEN** 手引きを変更したコミットを作る
- **THEN** 所有者の端末で、core を家の私的な語の一覧で検査し、当たらないことを確かめている
- **AND** 当たったときは、一覧を変えずに手引きの文章を役割の名前で書き直している
