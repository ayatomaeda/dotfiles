# Design

## Context

動機は proposal.md の Why。手引きは 11 節で、6 節 (346 行) が家の Claude Code の宣言の写し。6 節を指す参照が
2 節・7 節・8 節に 7 か所ある。読み手の記述 (1 節) と `CLAUDE.md` の読み込み (2 節) はエージェントを前提に
書かれている。spec `consumer-guide` は読み手を「エージェント」と定め、覆う範囲に「Claude Code を宣言する場合の形」
を含む。手引きの鮮度は家の CI (AI のレビュー) が保ち、家の側は対象のパスの一覧 (ステータスラインのディレクトリを
含む) を持つ。

## Goals / Non-Goals

**Goals:**

- 手引きから特定のエージェント製品の宣言を外し、エージェントを使わない利用側でも読める形にする。
- 6 節に頼っていた説明 (秘密の扱い、lock の更新の注意) を、6 節無しで成り立つ文にする。
- spec を、製品名を持たない形にそろえる。

**Non-Goals:**

- core の `CLAUDE.md`、モジュールのコメント、`terminal-tooling` の要件を変えない。これらは「非対話のエージェントが
  同じシェルを使う」という core の振る舞いの根拠で、製品の宣言ではない。
- `README.md` の「エージェントの設定は利用側が持つ」の原則と、その下の移行の節を変えない (済んだ移行の案内を縮めるのは別件)。
- 家の側の変更 (レビューの対象のパスの一覧、lock の更新) は core の change に含めない。

## Decisions

- **D1. 6 節は家へ「移す」のではなく削る。** 6 節の各項 (宣言のコード片、`package = null`・marketplaces・`claude mcp add`
  の注意、保存されない操作の表、各 Mac の後片付け) は、家の `README.md` と `CLAUDE.md` にすでに同じ内容がある
  (家のほうが新しい行も持つ)。家へ写すと二重になる。退けた案: 6 節を家の `docs/` に文書として移す — 家の README と
  重なるだけ。
- **D2. 読み手は「人か、エージェント」に広げ、エージェント向けの形は条件付きで残す。** 2 節の `CLAUDE.md` の小節と
  構造の木の `CLAUDE.md` の行は「エージェントに core の `CLAUDE.md` を読ませるなら」の形にする。Claude Code 以外の
  エージェントを使う利用側がそのまま読めるようにするため。退けた案: エージェントの記述をすべて消す — 7 節の
  「エージェントは `darwin-rebuild build` までを行う」のような役割の分担は、人が作業する場合にも同じ (所有者が switch
  する) で、消すと役割の記述が無くなる。
- **D3. 7 節の「6 節の assertion」は、宣言を外す変更の一般的な扱いとして書き直す。** 「core が宣言を外す変更は lock の
  更新と宣言の追加を 1 コミットにする」は製品に依らない。assertion は「利用側が、lock だけを上げた世代を評価で止める
  assertion を持つなら」の形で触れる。herdr の skill の注意 (build を通す) は、家の `herdr-skill.nix` の説明が 6 節に
  しか無いので、「lock の更新で herdr が上がったら `darwin-rebuild build` を通す (評価では止まらない生成物があるため)」
  と、生成物の名前を出さずに残す。
- **D4. 8 節の MCP のキーの例は残し、6 節への参照だけを外す。** 「秘密として扱わない資格情報を別のファイルに分け、
  エージェントが宣言を読むたびに値が文脈に入らないようにする」は、製品に依らない秘密の扱いの判断で、1Password の案を
  退けた経緯もここにしか無い。
- **D5. 初回の手順の「Claude Code を native インストーラで入れる」は削る。** 利用側が使うエージェントの導入はその
  利用側の文書に属する。2 節の `flake.nix` の例から `anthropic-skills` の input も外す (6 節のためだけにあった)。
- **D6. spec の Scenario「Claude Code の宣言を載せる」は「利用側のツールの宣言を載せる」に替える。** 検査の対象
  (資格情報は値ではなく読む形だけ、固有名を含まない) は製品に依らず、残す価値がある。「特定のエージェント製品の宣言を
  載せない」は、覆う範囲の要件の中に MUST NOT として足す (既存の要件の MODIFIED にする)。Scenario の差し替えは
  MODIFIED では archive が落とさない (validate で実測) ので、「手引きに私的な情報を書かない」は REMOVED にし、同じ本文を
  「手引きに私的な情報と資格情報の値を書かない」として ADDED で置く。
- **D7. 節番号は繰り上げる。** 「6 節 (削除)」の空き番号を残さない。手引きへのリンクは見出しの文字列でなく節番号で
  書かれているので、繰り上げ後に 7 か所の参照 (2 節 ×3、7 節 ×2、8 節 ×1、cask の例 ×1) をすべて直す。

## Risks / Trade-offs

- [家の CI が、この core の版へ lock を上げる PR で「影響あり」と判定する] → 想定どおりなら「影響なし」になる
  (手引きに Claude Code の節が無いので、家の Claude Code の変更は手引きに影響しない)。「影響あり」が出たら、レビューの
  プロンプトか対象の一覧が 6 節の存在を前提にしていないかを家の側で見る。
- [将来、別の利用側が再び Claude Code を使う] → 6 節の内容は家の文書と、この change の archive の前の版 (git の履歴)
  にある。必要なら家の文書から一般化し直す。
- [公開の前の検査] → 6 節の削除は語を減らす方向なので当たりにくいが、書き直す文 (読み手、assertion、herdr) は
  役割の名前で書き、`scripts/check-core.sh` を通す。

## Migration Plan

1. core: 手引きと spec を直し、`最終照合:` を改め、公開の前の検査を通して PR にする。
2. core の PR をマージした後、家: `nix flake update core` を PR にする。その PR で、レビューの対象のパスの一覧から
   ステータスラインのディレクトリを外す。家の CI のレビューは「影響なし」になるはず。
3. 戻すときは core の PR を revert する。生成物は変わらないので switch は要らない。
