## Why

core を flake の input にする利用側は、所有者の家の構成と、これから会社の PC で作る会社の構成の 2 つになる。
利用側の作り方と運用の知見 (リポジトリの形、値の置き場所、Homebrew の方針、Claude Code の宣言、lock の更新と
switch の手順) は、いま家の構成 (private) にしか無い。会社の PC からは家の構成が見えず、core だけが見えるので、
会社の構成を作るエージェントは、その知見を読めないまま同じ検討をやり直すことになる。

## What Changes

- core に、利用側の構成の作り方と運用を一般化した手引き `docs/CONSUMER-GUIDE.md` を置く。読み手は、core だけが
  見える端末で利用側のリポジトリを作って運用するエージェント。
- 手引きは「家ではこうしている」と「その理由と前提」を書く。読み手の環境への合わせ方は読み手が判断し、手引きは
  指示しない。
- 家の固有名 (ホスト名、ドメイン、アドレス、クラスタ、認証基盤の値、ユーザー名、家でだけ使うアプリの名前) は
  書かない。家に固有の部分は「こういう種類のものが家の側にある」までに留める。Claude Code の宣言 (settings、
  ステータスライン、MCP、skills、OpenSpec のコマンドの生成、herdr の skill、core だけを上げた lock を止める
  assertion) は、固有名を抜いたコード片として載せる。
- core の README と CLAUDE.md にすでにある仕組みの説明は写さず、リンクで参照する。
- 手引きの冒頭に `最終照合: YYYY-MM-DD` の行を置く。手引きの鮮度は利用側 (家) の仕組みが保ち、core は最終照合の
  日付を持つ。
- 利用側から core と家へ返したい知見は、利用側のリポジトリに私的な情報を含まない申し送りとして残し、人間が
  持ち出す。利用側から core を直接変えるときも core の公開の決まりに従う。手引きにこれを書く。
- core の `README.md` と `CLAUDE.md` から手引きへ案内する。

## Capabilities

### New Capabilities

- `consumer-guide`: core が、利用側の構成の作り方と運用の手引きを持つこと。手引きの読み手、書く内容と書かない内容、
  core の文書との関係、最終照合の日付、利用側から知見を返す経路を定める。

### Modified Capabilities

(なし。`dotfiles-management` の「環境固有の値と私的な情報を書かない」は、新しい文書にもそのまま及ぶ)

## Impact

- **文書:** `docs/CONSUMER-GUIDE.md` (新規)、`README.md` (ファイルの表と案内)、`CLAUDE.md` (冒頭の案内)。
- **コード:** なし。モジュール、option、生成物は変わらない (drvPath の照合は要らない)。
- **利用側:** 家の構成は、手引きを照合する仕組みを自分の側に持つ (家の側の change)。core はそれを参照しない。
  会社の構成を作るエージェントは、core のクローンから手引きを読む。
